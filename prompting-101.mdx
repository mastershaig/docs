## Writing Steps

Testavi reads the first word of each step to decide what kind of step it is, and the
editor shows a coloured badge for each kind:

<Columns cols={2}>
  <Card title="Action" icon="hand-pointer">
    Click, Type, Hover, Scroll, Wait, Upload, or Select — the things the test *does*.
  </Card>
  <Card title="Verify" icon="circle-check">
    A **hard** check — the test fails if it is not true. See [Verify vs Check](/verify-vs-check).
  </Card>
  <Card title="Check" icon="triangle-exclamation">
    A **soft** check — recorded as a warning but does not fail the run.
  </Card>
  <Card title="If / skip" icon="code-branch">
    A [conditional step](/conditional-steps) for optional elements — "If … otherwise skip".
  </Card>
  <Card title="Remember" icon="bookmark">
    Capture a value from the page to reuse in a later step. See [Variables](/variables).
  </Card>
  <Card title="JavaScript" icon="code">
    Run custom JavaScript code (start the step with `//`). See [JavaScript Actions](/javascript-actions).
  </Card>
</Columns>

## Best Practices

1. **Start Simple**: Begin with discrete actions for common interactions
2. **Validate Early**: Use [Verify](/verify-vs-check) steps to catch issues quickly
3. **One thing per step**: Keep actions and checks in separate steps
4. **Capture, don't repeat**: Use [Remember](/variables) to reuse a value instead of hard-coding it
5. **JavaScript as Backup**: Use JavaScript actions when other options aren't sufficient

## Common Pitfalls

1. **Multiple Actions**: Combining multiple actions in one step
2. **Vague Descriptions**: Using unclear element descriptions
3. **Missing Brackets**: Forgetting to enclose values or elements
4. **Skipping Verifications**: Not validating important states
5. **Implicit Waits**: Not specifying wait durations
