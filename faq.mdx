## How do you handle auth states?

Check out [**this page**](#), where we lead you through this. Essentially, we save cookies, local storage, and session storage states from Login Tests. Users can load them into relevant tests that require authentication by doing “Start from logged in state”.

## How can I debug tests?

The [run page](/run-results) is built for this:

- **"What went wrong"**: a plain-English analysis that classifies the failure as a
  product bug, a test issue, or an environment issue, with expected vs. actual.
- **Step timeline + video**: click a step to seek the video; see before/after
  screenshots for the failed step.
- **Console & network tabs**: browser logs for the run, with filters.
- **Share links**: a public, no-login link to a run for Slack, Jira, or a PR.

## How can I edit tests?

Modify natural language instructions in seconds.

## How do you ensure test reliability?

Testavi does not rely on XPaths or Selectors to run tests. Each test run is an AI run—the agent dynamically looks at the page and browses, just like human users do.

Tests only fail if your User Story or Functionality changes—tests are independent of code changes.

## Can I add any code based actions?

Yes, we support Javascript injection within tests. Call REST endpoints, APIs, or any other custom functionality you want.

## Mobile Testing?

We support mobile web view testing, not Native App Testing at the moment, but it is in our roadmap for next year :)

## Security? Do you require access to my code base?

We require zero access to your codebase & only testing deployed URLs. All our software is hosted in secure cloud environment, and tests are run in a secure cloud environment

## How do you handle On-premise website testing?

We currently don't offer an on-prem solution. All our tests are running in the cloud. However, if you have any environments hosted internally, behind a firewall, or in VPN, you can give us a client cert or whitelist our IP to allow us to access your application.

## How do you run tests?

We run tests on our deployed cloud instance against the test URL you specify. It work on any deployed URLs — including Ephemeral URLs generated in your CI.

## Can I run the same test with different data?

Yes — use a [scenario table](/scenario-tables). Write the test once with `{{column}}`
placeholders, add a row per data variant (coupon codes, search terms, countries), and
run them all as a matrix. You can run all rows, selected rows, or just re-run the
failed ones.

## Can I test my store in other languages or currencies?

Yes. Set a [locale, timezone, and geolocation](/language-locale-testing) per test,
environment, or scenario row, and assert on the result — "Verify the page is in
German", "Verify prices are shown in EUR", or check for untranslated English text.

## How do environments and secrets work?

Each suite can have several [environments](/environments-and-secrets) (Production,
Staging, …) with a base URL, variables, and secrets. Secrets are encrypted at rest,
masked in evidence, and the API only ever returns secret names — never values.

## Can I schedule tests and get notified?

Yes. [Schedule](/scheduling) a suite on an interval, at a time of day (with
timezone), or on a cron expression. Get one summary per suite run via
[Slack, email, or a webhook](/notifications).

## Why are re-runs so fast?

On a re-run, steps that passed before are replayed deterministically and self-heal if
the page changed; only **Verify** steps are re-evaluated fresh. See
[Fast re-runs](/fast-re-runs). Tip: end every test with a Verify step.

## Can I use Testavi from an AI assistant or scripts?

Yes. Create an [API key](/api-keys) and use the [MCP server](/mcp-server) from Claude
Code, Claude Desktop, or Cursor to author, run, and debug tests.
